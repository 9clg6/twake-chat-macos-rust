# Encryption, recovery, verification, devices

Part of [feature-inventory.md](../feature-inventory.md). Final behaviour per decision (Dnn of the React repo `DECISION.md`); later decisions override earlier ones. `modified by` = later entries that replace, update, complete or narrow this one (read them together; the latest wins). Entries with `superseded-by` are dead and listed at the end.

> **Settled: encryption default of a new direct chat.** D140 (2026-10-09) said every direct chat is encrypted; **D203 (2026-10-16) reverses that point**: a direct chat opened by clicking a person starts **in the clear**; the Synapse module no longer adds `m.room.encryption`. **D397 (2026-10-26)** keeps D203 and adds, on the empty-chat card of a clear direct chat, "This conversation is not encrypted." plus an "Encrypt this chat" button (for whoever may send `m.room.encryption`); after the press the card ticks "End-to-end encrypted messages". Groups: switch "End-to-end encryption", off by default; never encrypted and public. Only the assistant room is encrypted from creation. Encryption can only be turned on, never off. Code agrees: `src/ui/CreateRoomScreen.tsx` sends `isEncrypted` only for `kind==="group"` when the switch is on and the room is not public. Final rule: **DM = clear + offer to encrypt (D203, D397); group = clear unless switch; assistant room = encrypted.**

## Acceptance criteria (from e2e test bodies)

### e2eA: Devices / security

- [chat.e2e.ts] Given settings > security (`open-settings` > `open-security`) Then `device-list` contains "This device", first device row "Verified"; a device with no published keys reads "Can't read encrypted messages" and has no `device-verify`.

### e2eC: Encryption

- [encryption] Given alice sends a message in an encrypted room and it leaves "sending" (no `message-sending`) When she signs out, storage is emptied, and signs in on a new device Then `device-unlocked` is attached, the message is visible (key from the server key backup), and no `undecryptable` element exists.
- [encryption] Given an encrypted group of alice and bob (bob joins at once on invitation, D248) When each writes Then the other app decrypts it (0 undecryptable on both sides), and the server event content has `ciphertext` and never the plaintext.
- [encryption] Given a room in the clear that is switched to encrypted later When messages are sent after the switch Then bob (who was in the room, app open) reads them and the server holds only `ciphertext`; messages before are untouched.
- [encryption] Given a member added later via "Add members" in room info When he appears in the members panel Then his `member` row contains "Invited"; after he joins (D248) and opens a new device, he reads only messages sent after he joined, none before (key made for members of that time).
- [encryption] Given bob's message in an encrypted room When alice's device is wiped and she signs in again Then her backup holds bob's session key (`session_id` is a string) and she reads it.
- [encryption] Given a history longer than two pages (page = 30 messages) written in the app When the room opens Then the latest line shows and line 1 does not; the button "Load earlier messages" pages back until line 1 shows; every line is read (count of `message` matching the stamp equals the total), 0 `undecryptable` ("Unable to decrypt").
- [encryption] Given alice opens `/rooms/<id>?user=@bob:localhost` (profile panel) When bob prints SAS emojis and both confirm Then `verification-emojis` shown equal bob's printed emojis; `verification-dialog` contains "Person verified"; after "Close", `profile-verify` contains "Verified".
- [new-device] Given a browser that noted the devices of alice (`twake-chat.seenDevices:*` key) When another client logs in as alice with display name "Stolen laptop" Then `new-device-notice` contains "Stolen laptop" (within 60 s); clicking `new-device-yes` removes it; no notice at first load (D14).
- [identity-reset] Given a device nothing can unlock (stranded identity) When signed in Then `security-banner` contains "no recovery key and no key backup", has a `security-banner-reset` button; after clicking it `identity-reset` is visible and is a text button (class `MuiButton-text`, not an outlined pill).
- [identity-reset] Given the reset is confirmed via the "Reset" button of the dialog When the click happens Then exactly one popup is opened by the click itself, blank (`url: ''`, allowed), later pointed to `/auth/m.login.sso/fallback/web`; sign-in itself opens no popup.
- [identity-reset] Given a completed reset When settings opens Then `settings-security` contains "Your identity was reset. The new recovery key is kept by your Twake account."; signing out/in gives `device-unlocked` with no `security-banner` and no server proof asked.
- [identity-reset] Given a reset whose identity proof fails When settings opens Then `settings-security` contains "Your identity was not confirmed", no `security-banner`, and the row `device` containing "This device" shows "Verified" and not "Not verified" (#687).
- [discard-session] Given an encrypted room When alice sends "/discardsession" with Enter Then nothing goes to the room (last event is still the previous message), `message-notice` contains "Your next message in this conversation will use new keys.", input is empty, and the next message has a new `session_id` (the two messages before shared one).
- [discard-session] Given a room not encrypted When "/discardsession" is sent Then an `alert` contains "This conversation is not encrypted.", input empty, nothing sent.
- [store-at-rest] Given an encrypted room (D218) When IndexedDB is read Then the crypto DB (exactly 1) is more than 1000 chars, contains neither "@alice:localhost" nor "diffie_hellman_key", and a wrapped store key exists; after reload the earlier message is still read and the next one is sent encrypted (`ciphertext`), neither stuck in "sending".
